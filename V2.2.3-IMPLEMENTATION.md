# CyberTech 360 V2.2.3 — Real GRC Operations

V2.2.3 replaces the remaining demo-only write paths with authenticated, tenant-scoped operations.

## Implemented

1. Login screen using Supabase Auth email/password sessions.
2. User/role administration for existing tenant profiles; role changes restricted to super_admin/it_admin.
3. Persistent risk CRUD.
4. Persistent control CRUD and effectiveness assessment fields.
5. Private evidence upload with browser SHA-256 hashing and organization-scoped storage paths.
6. Persistent remediation workflow.
7. PCI DSS scope component register.
8. PCI assessment and requirement-item workflow with live scoring.
9. Compliance dashboard calculated from persistent control/assessment records.
10. Read-only audit trail populated by database triggers.
11. Vulnerability CRUD.
12. Organization/tenant administration with RLS-protected tenant edits.
13. AI GRC Copilot Edge Function reads live risks, controls, remediations and vulnerabilities; an external AI provider is optional.
14. Authorized GRC API Edge Function validates the bearer token, resolves the user profile/tenant, enforces role-based writes and relies on RLS.

## Supabase deployment order

Run these migrations in order:

1. `supabase/schema.sql`
2. `supabase/v2.2-production.sql`
3. `supabase/v2.2.1-security-hardening.sql`
4. `supabase/v2.2.2-compliance-engine.sql`

Then deploy Edge Functions:

```bash
supabase functions deploy health
supabase functions deploy auth-context
supabase functions deploy grc-api
supabase functions deploy bootstrap-organization
supabase functions deploy ai-grc-copilot
```

## Browser configuration

Copy `supabase-config.example.js` to `supabase-config.js` and set:

- `CT360_SUPABASE_URL`
- `CT360_SUPABASE_ANON_KEY`

Never place a Supabase service-role key in the browser or GitHub Pages.

## AI provider

The Copilot function supports:

- `AI_API_URL`
- `AI_API_KEY`
- `AI_MODEL`

These are Edge Function secrets, not browser configuration. If they are absent, Copilot returns a context-only response instead of inventing an answer.

## Authentication and MFA

Enable email/password authentication in Supabase Auth. For production tenants, enable and enforce MFA using the Supabase Auth project policy. The V2.2.3 login screen establishes the authenticated session; MFA enforcement remains a Supabase tenant configuration rather than a client-side security control.

## Production authorization model

The browser never supplies a trusted organization ID for authorization. PostgreSQL derives the organization from `profiles.organization_id` through `current_org_id()`. Write operations are additionally restricted by role through `can_write_gcr()`.

The `grc-api` function repeats authentication and role checks server-side and uses the user's bearer token so PostgreSQL RLS remains effective.

## Evidence

Evidence files are stored in the private `cybertech-evidence` bucket using:

`<organization_uuid>/<evidence_uuid>/<safe_filename>`

The browser calculates SHA-256 before upload and stores the digest in the evidence record. Use signed URLs for controlled retrieval.

## Important production boundary

The GitHub Pages frontend can now operate against Supabase, but it is not automatically a production deployment simply because the code exists in GitHub. Configure Supabase, apply the migrations, provision the first organization/profile, enable Auth/MFA, deploy the Edge Functions and configure the browser's public Supabase URL/anon key before treating the environment as live.
