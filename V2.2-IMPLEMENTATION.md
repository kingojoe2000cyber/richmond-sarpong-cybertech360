# CyberTech 360 V2.2 Implementation Guide

## What this release hardens
- Organization-aware PostgreSQL RLS.
- Server-side role lookup.
- Append-only audit history generated by database triggers.
- Private evidence storage with organization-scoped object paths.
- Evidence integrity metadata.
- Compliance assessments and remediation tracking.
- Risk register and compliance summary views.
- GitHub Actions dependency and CodeQL security gates.

## Supabase deployment
1. Create a Supabase project.
2. Run `supabase/schema.sql`.
3. Run `supabase/v2.2-production.sql`.
4. Run `supabase/v2.2.1-security-hardening.sql`.
5. Configure Supabase Auth and MFA.
6. Bootstrap the first organization/admin through a controlled server-side process.
7. Test two organizations and verify cross-tenant reads/writes are denied.
8. Keep the service-role key server-side only.

## Evidence storage
Store objects as:
`<organization_uuid>/<evidence_uuid>/<filename>`

The bucket is private. Signed URLs should be generated by an authorized backend operation rather than exposing the bucket publicly.

## Production boundary
The GitHub Pages UI remains demo mode until Supabase, authentication, backend authorization, private storage and environment configuration are connected. Synthetic records must not be presented as live telemetry.

## Authentication configuration
For a hosted Supabase-backed deployment, copy `supabase-config.example.js` to `supabase-config.js` and set only:
- `CT360_SUPABASE_URL`
- `CT360_SUPABASE_ANON_KEY`

Do not commit a service-role credential. Enable email/password and MFA in Supabase Auth before exposing production access.

The public GitHub Pages build remains demo mode until the configuration is supplied and the database migrations are applied.
